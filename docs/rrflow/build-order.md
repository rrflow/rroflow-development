# RRFlow build order (decided 2026-10-16)

Basis: rrflowKV is the canonical instance store, holding the project brain and the UI-managed config revisions (see `claude/compute-and-data-workload-classification.md`). Jesse chose "recoverability first".

What RRFlow is for (Jesse, 2026-10-16): "a collection of micro optimizations to bring together a smooth devspace and environment for the developer/context engineer." The capability study (`claude/rrflow-capability-study.md`) maps SurrealDB and Qdrant capabilities against that goal.

Direction (Jesse, 2026-10-17): RRFlow is "not wrappers ... not fragmented bits" but one platform built from the ground up, folding in the best of others, configurable, and extended with endpoints such as LFG and SWAG. The repo already enforces the first half: `AGENTS.md` treats SurrealDB, Qdrant, Lance and others as reference inputs only, re-authored at one RRFlow boundary and gate, never copied and renamed.
Three configurations plug into RRFlow (confirmed by Jesse, 2026-10-17). Endpoint configuration for all three rides on steps 2 (config revisions) and 4 (model endpoints).
- **LFG**: the CPU-based, optional configuration. It feeds SWAG data points such as complexity.
  - In the repo, LFG is Gate G: one adapter behind a provider-neutral `RouterBackend` (G-01), grammar-constrained to three routing decisions (G-03). The engine keeps planning, authorization and persistence.
- **SWAG** (named DALAL until 2026-10-17; concept unchanged): the System One controller, pluggable into RRFlow, and the official decision maker. Every model behind it is endpoint-configurable, so local or remote doesn't change what it does.
  - No repo record yet. It needs one before Gate G starts, stating which decisions it owns and what it may not touch, because the repo keeps planning, authorization and persistence in the engine (Gate G, ADR-0002).
- **RROFLOW**: the recursive self-improvement configuration, in which reason ready objects (RROs) improve themselves.
  - No roadmap item owns self-improvement. Nearest owners: Gate G's reasoning trees (G-04 commits recipe selection and branch navigation with the tree state) and Gate I's triggers, durable routines and skills (I-07 reacts to recurring failure signals).
  - Gate I's exit condition requires automation to be explicit, bounded, replayable, removable and subordinate to `RrdEngine`. Each self-improvement therefore lands as a versioned, authorized, reversible change, never as an automatic hook.
  - Inputs for its record: the earlier RRO design's five feedback loops (immediate reinforcement, reasoning-trace capture, consolidation, domain specialization through LoRA on the 0.6B minions, meta-reasoning), and Raindrop's loop, the reference Jesse named (workload class 7; weight updates are class 6).
  - Naming: the repo expands RRFlow as "Reason Ready Flow" and RRD as "Reason Ready Daemon" (`docs/architecture/system-overview.md`). It retired an older "RRO" term for a removed provisioning role (A-07, `docs/reference/security/authority.md`), yet the header comment of `crates/authority/rrd-security/src/lib.rs` still says "RRO provisions it". RRO as "reason ready object" needs a glossary entry in RROFLOW's record so the two meanings don't collide.

Proof of strength (Jesse, 2026-10-17): RRFlow "should absolutely be stronger" than SurrealDB and HydraDB. No proof exists yet: OBJ-10 (reproducible competitive evidence) is "Not established", POAM-012 records the missing benchmark, and J-04 allows no superiority claim until like-for-like evidence passes. "Stronger" needs two separate proofs: guarantees, through differential tests, and speed at matched quality, through the step 2b harness.

## Order

   - Also record (found 2026-10-16, night, driving Connectome): `diagnostics-read` cannot assemble under concurrent authenticated traffic.
     - Its consistency stamp (`capture_diagnostic_stamp`, `engine/diagnostic.rs`) includes the control sequence.
     - Every audited request, reads included, appends audit events to the control journal and advances it.
     - Under steady requests (the similarity map's searches), all `MAX_DIAGNOSTIC_ASSEMBLY_ATTEMPTS` (3) attempts change and the engine answers 409 `StorageConflict`, marked retryable.
     - Measured on the demo estate: the Storage lens could not read for the whole 47 s map build.
     - Fix direction, not decided: assemble from one storage snapshot, or keep audit appends out of the stamp.
   - Also record (found 2026-10-17 by Connectome's RRD process tests): `audit_since` in `crates/authority/rrd-security/src/lib.rs` fails a valid audit read.
     - It sets `reached_control_tail` whenever the last control-journal page it read was partial (`entries.len() < limit`), even when its inner loop stopped inside that page because the record limit was met.
     - So when the limit-th audit record lies in the journal's final, partial page and is not the head, it answers 400 InvalidArgument "audit chain does not reach its durable head".
     - Reproduced on every run against a fresh fixture estate with a 64-record audit page. A read from genesis fails for as long as the journal's length leaves that record in a partial final page; the demo estate's journal is long enough that its 64th audit record sits in a full page.
     - Connectome now reads one-record pages, which cannot trigger it: a non-empty one-record page is never partial.
     - Fix direction (analysis, not decided): set the flag only when a page was empty, or partial and fully consumed.
   - **Done 2026-10-17:** RRFlow PR #4, merged as `238e883` (merge commit, 17/17 candidate CI checks green). - One journal entry per step under `docs/evidence/change-journals/`.
